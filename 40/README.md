## Решение

Пять ключевых свойств системы  
1. Гарантия что сообщение будет обработано only-once: STRONG(1:1) "во всех состояниях x находится под контролем (в допустимом диапазоне)"

2. Смена УЗ которую используем для доступа к БД не сказывается на TPS БП: STRONG(1:1).   
Здесь говорится о системе, которая уже прогрета для пиковой TPS.  

3. Что будет пропускная способность основного БП 1000 TPS: STABLE(0:10) => RESILIENT(850:1000)  

4. Что у нас может быть только n служебных пользователей в данной роли: STRONG(1:...)  

5. Что система считается корректно сконфигуриррованной, если проходит "SmokeTest" взаимодействия компонент с кнопки в UI: STABLE(0:1)    
При условии что прошло время требуемое для запуска сервисов.   
0:1 - Либо система в корректном состоянии, либо один или несколько сервисов надо донастроить и в будущем она будет в корреткном состоянии.

>Какие инварианты в вашей системе можно усилить, что для этого надо сделать?

## Анализ

1. Отдельно разбирал разницу между TRIPWIRE и STABLE.   
В STABLE мы может несколько раз выходить из диапазона и возвращаться в него, на данном этапе не определенно время когда должны зафиксироваться в границах, просто говорится что этот момент будет. 

В TRIPWIRE у нас только одна попытка выхода из диапазона, а вторая уже будет ошибкой.  
STABLE может быть включен в TRIPWIRE, а наоборот - нет.
