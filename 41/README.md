## Анализ и решение
2. Важные структуры данных во многом существуют только на уровне спецификации, но в сериализации и коде, в который они приходят и из которого снова выходят сериализованные - в виде String.

Чуть лучше с XML, который при сериализации еще и описывает более строгие правила конкретных типов (паттерн, число повторение 0..1 или 1..n, вложенность одного типа в другой). 
Из-за того, что этот формат используется при взаимодействии более удаленных друг от друга комманд, которые сложнее синхронизировать, то проработан он лучше, чем формат обмена между близкими модулями. 

3. Первый вариант - даже не представляю. 
Первое что приходит на ум - делать полный equals, что бы доставать совпадающий объект. 
В качестве ключа использовать хэш объекта, как в HashMap. Но это ведь тоже id и завязывемся на единую хэш функцию. Ее либо держать на уровне единого хранилаща, но тогда больше передавать по сети, либо в общей библиотеке, версию которой надо держать синхронизированной во всей системе. 
А так id обычно передает как одно из полей DTO.


Без ORM - само собой, через, например, JdbcTemplate из Spring и самостоятельно написанные выражения. 

## Вывод
Еще раз взглянул на то, что с проверками типов в коде у нас есть куда расти.   
Проблема в том, что, если рефакторить, например, тип глобального id, то требуется перелопатить весь код проекта и этот рефакторинг сам понаделает багов, хотя и поможет в будущем. 

Учитывая "В идеале ПО не нуждается в хирургических подходах" - с ИИ это можно будет значительно быстрее переписать **заново**, при условии наличия IT написанных людьми.
