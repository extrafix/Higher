# Как правильно писать тесты

Я сделал прошлое задание не по той статье. 

> Найдите 5 своих (или чужих) примеров, когда тесты зависят от реализации, и переделайте правильно.

Код тестов с абстрактными эффектами использовать не могу.

1. 
АЭ: отправлено сообщение с результатом обработки в очередь.
Практически все юнит тесты. 
Проверяем отправку сообщений через конкретный объект. 
Ближайший к этому "абстрактный" эффект, что сообщение попало в очередь, которую могли бы проверять.

В целом, в IT(integration test) именно так и делаем. 
Но это уже и большая завязка на реализацию, если ActiveMQ заменим Kafka, например. 

Можно еще более "абстрактный" эффект тестировать на уровне того, что получает конечный клиент, что тоже проверяется на уровне IT, но это уже не дает модульности.
Для модульности "клиентом" выступает ближайший получатель результата. Будь то результат из чистой функции или сообщение в очередь.

2. UI тесты.
АЭ (абстрактный эффект): при получении с сервера такого-то списка отображаем в таблице столько-то записей и такие-то значения в таких-то полях.
Тестируется с помощью библиотеки мокирования для сервера + проверка ui и вбитие нужных фильтров через selenide.

3. Юнит тест.
АЭ: В GitLab проставляются в ревьюеры нужные пользователи, после снятия МР с Draft.
Мокаем класс API для GitLab и проверяем объект отправляемый в него на ожидаемые значения, который сформировались в теле метода, который тестируем.

4. Модульный.
АЭ: После хука от МР GitLab, парсим из хука нужную информацию об МР и вливаем его.
Тестируется через сохранение различных видов реальных json хук, которые приходили от GitLab, в связи с тем, что API описано плохо и контракт того, что может быть за набор полей, весьма не строгий. 

5. IT.
АЭ: При смене пароля для БД в системе управления паролями - новые соединения из приложения создаются бесшовно.
Программа работает без проседания производительности.

Тестируется с помощью смены пароля в 
а) БД
б) реальной системе управления УЗ
Проверяется, что дэшборд с нарушения SLA в этот момент и после максимального времени жизни старых соединений (30 минут) - пуст. 

С одной стороны, тут все как будто реальное, без моков. 
Но с другой, выполняется это на тестовой среде, и хотя объекты запросов которые обрабатывает система идентичны настоящим, в случае ошибки с ними это все еще ошибка в тесте, а не проде. 

**Важное**  
Иными словами, чувствуется, что система, которая по версии ПО идентична той, что установлена в проде, в случае использования ее на тестовой среде, скорее мок и есть. 
Хотя и завязанный с тонкостями реализации. 

Связь с "Три уровня рассуждения о программе", и мысли о том, что карта!=местность на ней изображенная.
